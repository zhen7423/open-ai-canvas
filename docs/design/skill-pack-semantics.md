# 技能套装：启用级联与本轮附带

口径来源：2026-10-28「老李漫剧套装」（1 总控 + 12 子技能）接入验证。

## 一、什么是套装

一个 GitHub 仓库里并列放多个技能目录时，平台只能一个目录装一次（`技能包包含多个 SKILL.md，请指定单个技能目录`，见 `backend/internal/skills/skill_packages_archive.go`）。于是「一套技能」在库里散成 N 条独立记录，用户必须逐个启用、逐个勾选才能在一次对话里用全。

**套装判定**：`SourceType == "github"` 且 `SourceURL` 相同的技能属于同一套（`backend/internal/skills/skill_packs.go`）。

- 判据只用安装时落库的规范仓库地址，不要求上游作者在 SKILL.md 里声明套装——上游没有这个字段，任何声明都可能缺失或写错。
- 非 GitHub 来源（zip 上传、单文件 markdown）与缺仓库地址的技能**不参与套装**，行为与改动前完全一致。
- 已知边界：`SourceURL` 按字符串精确匹配（只裁掉结尾斜杠）。同一仓库若以不同大小写或带路径的形式装过两次，两次安装不会被认成同一套。

## 二、套装改变的两件事

### 1. 启用级联（写库）

启用套装里任意一个技能时，同套**公开 + 已上架**的技能一起加入该用户的技能库。

- 只写该用户自己的 `user_skill_states` 行；技能内容、上架状态、他人状态一律不动。
- 配套若已有状态行（例如先前被移出过、但用户给它留了自定义库分类或收藏），级联**复用那一行**
  （连 `id` 一起），只把 `added` 翻成 true。加入用的 upsert 会覆盖 `library_category_id`，
  拿全新空行去盖就会把用户自己选过的分类抹掉。
- 主技能与配套在**同一事务**里写（`SetUserSkillAddedBatch`）：要么整套启用，要么一条都不写。
- 作者本人的技能恒在库中，不需要写自己的状态，但**级联照跑**——别人安装的同套配套同样要连带启用。
- **移除不级联**：取消一个不会把整套踢出技能库。要整撤就逐个撤，加入时已如实报过连带启用了哪些。
- 上限 32（`skillPackCompanionLimit`，只数配套、不含被点的那个）：超过说明该仓库装的不是同一套技能，宁可不带。
- 响应带 `packAutoAdded`（本次连带启用的清单），前端提示「已连带启用套装内 N 个配套」用的就是它；
  `packKey` 是套装标识，当前只作为数据出口（尚未做按套分组的市场/库界面），不承诺 UI 效果。

### 2. 本轮自动附带（只读）

一次 Agent 请求里勾选了套装成员时，`cloudAgentSkills` 把该用户**已启用**的同套其余技能一起带进本轮快照，标记 `attachedVia: "pack"`，系统清单里原样带上，让模型知道这条不是用户勾选的而是套装附带。

- 附带走的仍是同一个快照构造函数，里面仍是那条边界：**已加入 + 已上架 + 对本人可见**。用户没启用的配套不会因为附带变得可读——附带只读不写。
- 附带是增益不是前置条件：查不到配套、或某个配套在读取时被删除/刚更新，只跳过那一个，不打回整轮请求。
- 上限 32（`cloudAgentPackAttachMax`，管的是**本轮快照的技能总数**）。级联那边另有一个 32
  （`skillPackCompanionLimit`，管的是**一次带出多少条配套**），两个数相等只是巧合，语义不同；
  真要调别把它们当成同一个数。超限的表现是「附带被悄悄截断」。
- 套装标识 `packKey` 与分组查询用同一个口径：原样存储的仓库地址，不做大小写折叠。
  因此大小写或结尾斜杠不同的两次同仓安装会被认成两套——这是有意选择（宁可少并，不可错并），
  改这里要同时改 `PackPublicSkills` / `PackAddedSkills` 的匹配条件。
- 因此用户只勾总控也能用整套，不需要逐个勾选，也不需要「全选当前」（那会把别的包一起挂上）。

### 3. 套装路径别名（只负责寻址）

总控把必读文件写成 `sd-script-engine/references/six-stage-pipeline.md` 这种「技能名/包内路径」，而平台按 `skillId` + 包内路径寻址。`skill_read_file` 先做一次解析：首段等于本轮某个快照技能的名字（忽略大小写与首尾空格）、且剩余路径确在该技能可读清单里时，改写到那个技能上；否则原样返回，继续走固定快照校验。

- 剩余路径写 `SKILL.md` 或包内相对路径都认；只写技能名（没有 `/`）不改写。
- **改写只发生在同套装内**：首段那支球队必须是「被勾选的这只」或「与被勾选技能 `Pack` 相同」的配套。
  库里同时装了原仓库和某个 fork、两只技能恰好同名时，不会被静默指到另一只上去。
- 同套装里出现两只同名技能时按**歧义**处理：不改写，让模型拿到原有的失败提示后改用真实 `skillId`。
  宁可读失败，也不能读到另一只技能的版本和内容却没有任何提示。
- 别名**不放宽权限**：改写后仍然只能读快照里列出的路径，读不到的照旧报错。
- 使用统计按**真正被读的那只技能**归账（事件负载里的 `skillId`/`skillName`/`path` 是解析后的，
  原始请求留在 `requestedSkillId`/`requestedPath`）。不然子技能卡片的读取会全记在总控名下，
  「技能使用」面板就会把套装的贡献全算到一只技能上。

## 三、已知缺口（本轮只记录，不改动）

套装的**机检环节在平台上无法履行**，与启用与否无关：

- 技能快照只收 `.md/.txt/.json`（`cloud_agent_tools_skills.go`），老李套装 144 份 markdown 能读，**19 个 Python 脚本读不到**——`validate_prompt.py`（总控 15 个脚本之一）、`sd-feed-engine/scripts/gate_check.py` 六道闸门、`check_asset_blocks.py`、`style-lock-ladder.py` 等全部落在这 19 个里。
- 画布 Agent 没有代码执行工具，即使读到脚本内容也不能跑；平台不会替用户执行技能里写「必跑 scripts/xxx.py」这类步骤。
- 因此总控里以脚本为硬门的步骤（P2 资产块自检、P4 六道闸门、P5 机检清零）在本平台上只能降级为「按规则清单人工逐条自检」。若要真正闭环，需要单独讨论执行通道（沙箱/白名单），那是新的能力面与安全面，不在本次改动范围内。

### 级联与附带的可计量副作用（本轮只记录，不改动）

- **市场统计被放大**：`addedCount` 与「热门」排序都按 `user_skill_states.added` 计数
  （`repository/skills.go` 的 metric 子查询）。启用一只总控会给同套最多 32 只公开技能各写一行
  `added=true`，于是「把一份内容拆成 N 个目录」就能让统计放大约 N 倍。不改技能本体、不改他人状态，
  但统计口径要清楚它现在数的是「进过库」而不是「被作者装过」。要区分得给状态行加来源标记（新列＝新迁移）。
- **每轮成本随套装规模线性上升**：每个附带配套都要跑 2 次 `SkillDetail`（各约 6 条 SQL）加一次
  包快照校验（解 ZIP、逐文件 SHA256，无缓存）。13 只一套 ≈ 150+ 条查询与 13 次归档扫描，
  外加每个被勾选的 master 每轮多 1 次 `PackAddedSkills`。快照里的文件清单就是读取权限的边界，
  所以「先不列文件、读的时候再列」这条省法被否掉——那会把权限判断挪出冻结快照。
  `skills.source_url` 目前无索引，等值查询走扫描，量级上来后要先加索引。
- **上限只管附带，不管勾选**：`cloudAgentPackAttachMax` 的 32 是「本轮快照总数」，但请求里
  `req.SkillIDs` 本身没有数量上限，所以勾选 40 只照样是 40 只。多个 master 分属多个套装时，
  谁被带全取决于请求里 id 的顺序（即前端勾选顺序），被截断的部分目前只在实现层丢弃、
  不在事件文案里说明。真要钉死总量，得在 `validateCloudAgentRequest` 加一条并同步前端。

## 四、验证口径

- 后端单测：`backend/internal/skills/skill_packs_test.go`（级联只带公开已上架、幂等、移除不级联、自有技能也级联、非套装保持旧行为、附带只取用户库里已有的、级联到上限即停）；`backend/internal/app/cloud_agent_skill_pack_test.go`（附带集合、`attachedVia` 标记、未启用配套读不到并钉住边界文案、别名解析与失败回退）。
- 本轮同时改了 `skill_read_file` 的工具描述（说明套装路径别名），这属于工具契约变更：`testdata/agent_tools/full.json` 需按门禁口径用 `UPDATE_GOLDEN=1 go test -run TestCloudAgentToolSchemaGolden ./internal/app/` 重生成，并逐行评审 diff（应当只有那一行描述变化）。工具 schema 是模型契约也是 prompt cache 前缀第一段，别顺手改文案。
- 夹具坑：`CreateSkill` 会给创建者留一条 `added=true` 的 `user_skill_states` 行。要造「同套但用户未启用」的技能，必须同时把 `owner_id` 改走**并删掉该行**，否则它确实属于该用户的技能库，被附带是正确行为（本轮第一版用例就是这么红的，代码没错）。
- 未覆盖的一条：级联的**失败回滚**（同一事务里第二条配套写失败时主技能也不落）。现有测试在不给生产代码加失败注入钩子的前提下构造不出中途失败，所以「同一事务」目前只有实现和注释支撑，没有红测支撑——要补得先定注入点。
- 一个易踩的夹具坑：`CreateSkill` 会给创建者留一条 `added=true` 的 `user_skill_states` 行。要造「同套但用户未启用」的技能，必须同时改走 `owner_id` 并删掉该行，否则它确实属于该用户的技能库，被附带是正确行为。
- 线上验收要看的三件事：只启用总控的一次对话里 `skill_search` 能否命中子技能名；`skill_read_file` 读 `sd-xxx-engine/references/*.md` 是否成功；技能库加入总控后是否出现 13 条「已加入」。
